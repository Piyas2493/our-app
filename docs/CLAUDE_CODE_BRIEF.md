# JeevanLink — MVP & Deployment Brief for Claude Code

_Generated by Claude (Cowork) on 2026-09-10 after auditing this repo against the SIH-26047 problem statement ("Patient Case-Taking Software" / MediKiosk, All India Institute of Ayurveda, Ministry of Ayush). Read this whole file before touching code — it tells you what exists, what's fake/stubbed, and what to build next, in priority order._

## 1. What the problem statement actually asks for

Full text lives at the project owner's side as `SIH26047.pdf`; the load-bearing requirements are:

- **Module A — Conversational multimodal history engine.** Patient speaks or taps through a structured clinical history interview (chief complaint → HPI via SOCRATES framework → past medical/surgical → drug/allergy → family → personal → review of systems). Dual-mode input (every question answerable by voice OR touch). Adaptive questioning that branches on answers. A dedicated AYUSH mode capturing Dashavidha Pariksha (Prakriti, Vikriti, Sara, Samhanana, Pramana, Satmya, Sattva, Ahara Shakti, Vyayama Shakti, Vaya) and Ahara-Vihara. AI red-flag detection on emergency symptoms (chest pain + dyspnoea, stroke signs, etc.) that triggers priority triage instead of routine queueing.
- **Module B — Medical document digitization.** OCR (printed + handwritten, multilingual) on prior prescriptions/lab reports/discharge summaries. Intelligent extraction of diagnoses, medications+dosages, investigation values. Automatic chronological ordering of documents into one coherent timeline. Abnormal-value and drug-interaction highlighting.
- **Module C — Structured history summary generator.** Synthesizes the conversation + digitized documents into one physician-ready summary in standard format (Chief complaint → HPI → PMH/surgical → Drug & allergy → Family → Personal → ROS → Prior investigations). Must be editable/verifiable by the physician, never an autonomous diagnosis. Bilingual output (patient-facing audio in local language, physician-facing text in English/Hindi).
- **Module D — Consent, privacy, ABDM integration.** Patient authenticates via ABHA ID. Granular, revocable, audio-explained consent (DPDP Act 2023 + ABDM consent framework). Structured history pushed to hospital HIS/EMR and linked to the ABHA Personal Health Record via FHIR APIs. Session data cleared immediately after submission.
- **Accessibility.** Audio-guided mode for visually impaired, large-text/high-contrast mode, multilingual UI, sign-language avatar (explicitly a stretch goal in the PS itself).
- **Patient dashboard.** Login + stored records.
- **End-to-end journey.** Identify (ABHA/Aadhaar login, language, consent) → Converse (adaptive voice+touch interview, red flags trigger triage) → Scan (upload/OCR/digitize/timeline prior documents) → Summarize & Route (generate summary, push to ABHA/HIS) → Consult (physician reviews/edits/confirms in seconds).

## 2. What's already built in this repo (verified by reading the code, not assuming)

Stack: Next.js 16 + React 19, Prisma 6 + SQLite (dev), Tailwind 4, Google Gemini (`@google/genai`, model `gemini-3.6-flash` / TTS model `gemini-3.1-flash-tts-preview`) as the AI backbone. `openai` is a listed dependency but **no route in the codebase currently calls it** — check before assuming it's wired up anywhere new you touch.

- **Clinical intake** (`src/app/clinical-intake/page.tsx`, `src/app/api/clinical-intake/route.ts` + `speak/` + `transcribe/`): dual-mode voice/touch intake page exists, AYUSH branch exists (Prakriti/Vikriti/Dashavidha terms confirmed in the file), multilingual via `LanguageProvider`/`LanguageSwitcher` + a large `src/app/lib/i18n.ts`. Voice capture is real: `transcribe/route.ts` sends recorded audio straight to Gemini for STT, `speak/route.ts` calls Gemini TTS and returns a WAV. Red-flag detection is implemented in `buildRedFlags()` inside `api/clinical-intake/route.ts` — **but it is plain English keyword/substring matching** (chest pain, severe breathlessness, unconscious, facial droop, severe bleeding, etc.), not model-driven, and has no non-English terms.
- **Document digitization** (`src/app/api/analyze-document/route.ts`, `upload-document/route.ts`): uploads are stored under `apps/web/private-uploads/medical/`, then sent to Gemini multimodal with a strict JSON schema (documentType, patient, medications w/ dosage, labResults w/ referenceRange+status, radiology findings/impression, warnings) and explicit anti-hallucination instructions ("do not diagnose," "do not invent," "empty string if unclear"). This is genuinely working OCR+extraction via LLM vision rather than a dedicated OCR engine.
- **Structured summary / clinician side** (`src/app/api/scribe/generate/route.ts`, `src/app/clinician/page.tsx`, `src/components/ClinicalSnapshotPanel.tsx`, `src/components/clinician/ClinicalHistoryPanel.tsx`): scribe endpoint turns free-form clinician notes into SOAP JSON via Gemini. Every `MedicalRecord` is created with `status: PENDING` and requires explicit clinician VERIFY/REJECT (`VerificationAudit` model logs every action) — this correctly implements "editable/verifiable, never autonomous."
- **Consent** (`prisma/schema.prisma` `ConsentEvent` model, `src/app/api/consent/route.ts`, `src/app/consent/page.tsx`): append-only consent log — a grant/revoke is a new row, never an overwrite, covering CLINICAL_HISTORY / DOCUMENT_PROCESSING / CLINICIAN_SHARING / RESEARCH_DATA_SHARING / REMINDERS_NOTIFICATIONS. This is solid and arguably exceeds the PS's ask. **"ABDM" and "FHIR" currently only appear as explanatory copy text on the consent page — there is no real FHIR resource generation or HIE call anywhere in the codebase.**
- **Auth** (`src/app/lib/auth.ts`, `src/app/login/page.tsx`, `src/app/api/auth/*`): cookie-based session (`jeevanlink_session`) against a `User` table with bcrypt password hashes and roles (PATIENT/CLINICIAN/HELPDESK/ADMIN). **No ABHA ID or Aadhaar-based login exists** — grep of `login/page.tsx` found zero hits for ABHA/Aadhaar/FHIR/ABDM/OTP.
- **Beyond the PS's scope** (already built, useful context but not required by the judges' rubric): hospital admissions/tests/procedures/billing/insurance claims (`hospitals-labs`), medication reminders + logs, vitals tracking from manual/wearable sources with an AI vitals report, `personalized-health`, a support ticket helpdesk with an admin overview, and a separate general-purpose `voice-assistant` (not the intake one).
- **Environment**: only `GEMINI_API_KEY` and a SQLite `DATABASE_URL` are configured. No Bhashini/AI4Bharat credentials, no ABDM sandbox credentials, no Postgres.
- **Repo hygiene flags**: `lintout.txt` (59KB) and `lintresults.txt` (66KB) are checked into `apps/web/` — these look like stale lint dumps, not source; either clean them up or add to `.gitignore`. No test files were found anywhere in `apps/web/src`.

## 3. Priority 1 — MVP (get this solid before the next demo/judging round)

Work top-to-bottom; each item names the exact files involved.

1. **Verify and, if needed, deepen the adaptive-questioning logic in `clinical-intake/page.tsx`.** This file is 1,400+ lines and was only keyword-scanned during the audit, not read end-to-end — confirm it actually branches per the SOCRATES framework (onset, location, character, radiation, alleviating/aggravating factors, timing, severity) rather than asking a fixed script. If it's a fixed script, add real branching driven by the chief complaint and prior answers.
2. **Harden red-flag detection.** Current `buildRedFlags()` is English-only substring matching on a short hardcoded term list. At minimum: (a) extend coverage to the languages the app already supports via `i18n.ts`, since a Hindi/Tamil/etc.-speaking patient's emergency symptom currently won't trigger anything; (b) consider routing the assembled intake text through Gemini with a "does this describe a medical emergency, and why" structured prompt as a second pass, since keyword matching alone will miss paraphrases ("felt like my chest was being crushed" won't match "chest pain"). Whatever you land on, make sure a positive red flag actually surfaces as a priority/triage signal somewhere a clinician or front-desk role sees it — confirm this end-to-end, not just that the flag gets stored on the record.
3. **Confirm (or build) the cross-document chronological timeline.** The PS explicitly wants prior documents dated and ordered into one coherent history for the physician, plus abnormal-value/drug-interaction flags *across* documents, not just per-document. `analyze-document/route.ts` extracts structured data per upload; check whether `health-timeline/page.tsx` actually merges multiple `MedicalRecord`s into a single ordered view with cross-record abnormal/interaction flags, or whether it's just a list. Build the merge if it's missing.
4. **Add the accessibility features the PS names explicitly**, since these are core requirements (not the stretch-goal sign-language avatar): an audio-guided mode for visually impaired/low-literacy patients (the app already has TTS via `speak/route.ts` — reuse it to narrate each intake screen) and a high-contrast/large-text mode toggle. Wire both into the existing `LanguageProvider`/settings pattern so they persist across the session.
5. **Reconcile the bilingual-summary requirement.** The PS wants the physician-facing summary in English/Hindi regardless of what language the patient spoke. Confirm `scribe/generate/route.ts` (or wherever the final Module-C summary gets built) actually produces this, or add an explicit translation pass.
6. **Clean up repo hygiene**: delete or gitignore `lintout.txt`/`lintresults.txt`, run `npm run lint` fresh and actually fix what it reports (65KB of prior lint output suggests there's a real backlog), and remove the unused `openai` dependency unless you have a concrete near-term use for it.
7. **Add minimal test coverage** for the three riskiest paths before a live demo: clinical-intake submission (`api/clinical-intake/route.ts`), document analysis (`api/analyze-document/route.ts`), and consent recording (`api/consent/route.ts`) — these are what a judge or a hospital pilot would actually exercise, and right now there isn't a single test file anywhere in `apps/web/src`.

## 4. Priority 2 — Stretch (only after MVP above is solid; explicitly deferred per project owner)

The project owner said the immediate goal is a demo-robust MVP, not real production/ABDM integration — treat everything below as backlog, not this sprint:

- Real ABHA ID login (replace/augment the email+password `User` auth with ABHA-based identification) and an actual ABDM sandbox integration generating real FHIR resources and pushing to a Health Information Exchange, replacing the current consent-page copy that just *describes* ABDM/FHIR without calling it.
- Swap or supplement the Gemini-based STT with Bhashini/AI4Bharat if accent/noise robustness in real OPDs turns out to matter — evaluate this with real recordings before committing engineering time to it.
- Session-data lifecycle: the PS envisions intake as a transient capture layer with data cleared after submission and pushed elsewhere; this app has instead become the system of record (full EMR in Prisma/SQLite). Decide deliberately whether that's the intended product direction (probably yes, given how much has been built around it) and document it, rather than silently diverging from the PS.
- Move off dev SQLite to Postgres, add a real hosting target, environment-based secrets, and basic monitoring/error tracking if/when this needs to run somewhere real.
- Sign-language avatar (explicitly a stretch goal in the PS itself — lowest priority of everything in this document).

## 5. Suggested order of operations

Start with item 1 (confirm what the intake flow actually does today — this determines how much of items 2–5 is "extend" vs "build from scratch"), then 2 and 4 together since they touch the same intake UI, then 3, then 5, then close with 6–7. Don't start on Priority 2 until Priority 1 is demo-tested end to end (Identify → Converse → Scan → Summarize → Consult) with a real red-flag case and a real AYUSH case walked through manually.
